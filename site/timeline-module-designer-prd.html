01

Executive summary

The Timeline Module Designer will replace hand-maintained Illustrator and SVG tile layouts with a constrained visual editor backed by reusable web components. The editor will expose one master module canvas, a property inspector, a content editor, and a live full-timeline preview. Every timeline instance will be rendered from the same component, data records, and design tokens.

The application will make global typography and geometry changes propagate automatically, allow event records to be added or removed without manual shuffling, preserve visible sample and placeholder copy, and prevent export while text or artwork is unresolved.

Product decision

HTML/CSS is the canonical authoring and rendering system. SVG and PDF are generated deliverables. Users must not need to edit the compiled SVG to maintain the timeline.

02

Problem statement

The current workflow treats each tile as independent vector artwork. That produces four recurring problems:

  1. Text is pre-broken into discrete SVG lines. Font, size, width, or copy changes require line breaks to be regenerated rather than allowing natural area-text flow.
  2. Repeated geometry is not truly shared. Resizing a panel, changing an inset, or moving a caption requires repeating the edit across twenty modules.
  3. Reference content can be lost during refactoring. Visible placeholder copy from the approved sample module was omitted because it was not modeled as structured product data.
  4. Adding or removing a record creates layout labor. Tiles, event dots, stems, era segments, and labels have to be repositioned manually.

The root issue is not simply an SVG limitation. It is the lack of a maintained component model, shared design tokens, structured content schema, and deterministic layout engine.

03

Product principles

01

One master, many instances

Every module derives from one component. Shared appearance is never copied into independently maintained artwork.

02

Content and design stay separate

Historical facts and image metadata belong to records; typography and geometry belong to design tokens.

03

Direct manipulation edits constraints

Drag handles change meaningful shared properties such as width, inset, or photo height—not arbitrary per-tile coordinates.

04

Generated output is disposable

PDF and SVG can be rebuilt at any time from canonical inputs and should never contain the only copy of a decision.

05

Failure must be visible

Overset text, missing images, unavailable fonts, and insufficient resolution are explicit warnings, not silent defects.

06

Print geometry is deterministic

The same data and tokens must always produce the same tile positions and export bounds.

04

Goals and scope

Goals

  • Edit a single master module visually.
  • Use genuine browser text flow inside bounded headline and caption areas.
  • Propagate design changes to every module immediately.
  • Recalculate the five-degree timeline when records are added, removed, reordered, or reassigned.
  • Preview short, long, missing, and representative content states.
  • Preserve the visible sample content from timeline-module-master-v2.
  • Produce a repeatable print-scale PDF and compiled SVG.
  • Protect historical content, provenance, and copyright metadata.

Non-goals for MVP

  • Replacing Illustrator as a general-purpose drawing application.
  • Supporting arbitrary freeform layouts for individual events.
  • Multi-user accounts, comments, or simultaneous editing.
  • Performing final CMYK conversion inside the browser.
  • Full photo retouching or restoration.
  • Round-tripping hand edits from generated SVG back into the component model.
  • Generating a fully editable Illustrator file in the initial release.

05

Users and jobs

Primary

Timeline designer

Needs to tune hierarchy, typography, spacing, and module proportions once and trust that every event will update.

Primary

Historical editor

Needs to update dates, headlines, captions, photos, rights, and ordering without manipulating layout geometry.

Secondary

Print-production reviewer

Needs predictable dimensions, embedded fonts, image-resolution checks, and a clear preflight report.

Core jobs to be done

When I change a font or text size, I want every module to update and reflow so that I can judge the complete timeline without editing twenty objects.

When I resize part of the master module, I want all instances and the overall layout to recalculate so that the composition remains coherent.

When I add, remove, or reorder an event, I want dots, stems, modules, and era segments to rebuild automatically so that no manual shuffling is required.

When I prepare a print export, I want blocking problems identified before the file is generated so that errors do not reach the wall.

07

Functional requirements

P0 required for first usable release P1 next iteration P2 optional extension

MD-01P0

Shared module component

The module canvas, complete timeline, and print renderer must use the same component implementation and token set.

  • No duplicated geometry definitions between editor and export.
  • All twenty current modules must render from the component.
  • Generated SVG must identify its source data and token revision.

Acceptance: Changing module width once updates every on-screen module and the regenerated output without editing an instance.

MD-02P0

Direct module canvas

Users must be able to select and manipulate the master’s named regions visually.

  • Handles for module width, headline height, lower-module height, photo/caption division, content inset, rule width, stem length, radius, and shadow offset.
  • Rulers display full-size inches while the canvas is zoomed.
  • Drag operations snap to a configurable increment, defaulting to 0.05 full-size inches.
  • Inspector values remain keyboard editable.

Acceptance: Dragging the photo/caption divider updates the token, all module instances, and overflow results in one operation.

MD-03P0

Flowing text areas

Headline and caption copy must be stored as continuous strings and rendered inside bounded HTML text areas.

  • No persisted line breaks generated solely for visual wrapping.
  • Font, size, weight, leading, alignment, and inset are shared tokens.
  • Explicit editorial line breaks remain possible and are distinguished from automatic wrapping.
  • Overflow state recalculates after any text or geometry change.

Acceptance: Changing the headline font causes every headline to reflow without modifying content records.

MD-04P0

Structured content editor

Each event record must expose date, headline, caption, image, era, reference number, rights, credit, provenance, and review state.

  • Reordering uses drag-and-drop plus keyboard controls.
  • Adding and deleting require stable record IDs.
  • Deleting a placed event requires confirmation and does not delete its catalog photograph.
  • Design edits and historical-content edits have separate undo labels.

Acceptance: Adding a twenty-first event creates a module, dot, two stems, and correct timeline position without manual placement.

MD-05P0

Automatic ramp layout

The layout engine must calculate module positions, timeline endpoints, event dots, stems, era segments, and era labels from the ordered record set.

  • Default ramp angle is 5°.
  • Modules remain level and share a consistent vertical relationship to the line.
  • Pitch may be fixed or fit-to-width, selected as a global layout mode.
  • Four eras remain contiguous and must cover every event exactly once.

Acceptance: Removing any event closes the sequence and rebuilds every dependent element with no orphaned geometry.

MD-06P0

Stress-test previews

The module canvas must switch among representative content fixtures without modifying production data.

  • Current event, longest date, longest headline, longest caption, empty-photo state, and each era color.
  • A preserved timeline-module-master-v2 fixture containing the visible sample year, headline, and caption.
  • Spec-annotation copy from that source is explicitly excluded.

Acceptance: The sample fixture visibly contains “1911,” “Voters establish the Beaumont Library District,” and “Beaumont Bank / Funk Building — first home of the library.”

MD-07P0

Design-token persistence

Shared design properties must be saved as named, versioned tokens rather than inferred from generated artwork.

  • Export and import JSON token files.
  • Autosave a local working draft.
  • Restore approved defaults.
  • Maintain undo and redo across direct manipulation and inspector edits.

Acceptance: Reloading the application restores the most recent local draft, while “Restore approved” returns the committed token set.

MD-08P0

Preflight and blocking warnings

Preflight must run continuously and again before export.

  • Detect headline or caption overflow, missing required copy, unavailable fonts, missing photos, insufficient image resolution, invalid era coverage, and artwork outside print bounds.
  • Warnings link directly to the affected record or token.
  • Blocking errors prevent production export; nonblocking warnings require acknowledgement.

Acceptance: A deliberately overset headline prevents PDF export and selects the offending module.

MD-09P0

Deterministic export

The application must export a 1:10 print PDF, a compiled SVG, and a machine-readable manifest from the same rendered state.

  • Full-size mural dimensions are 356 × 120 inches; default output is 35.6 × 12 inches at 1:10.
  • Fonts are embedded in PDF when licensing permits.
  • Photos use the selected crop and sufficient effective resolution.
  • The manifest records data revision, token revision, font list, image list, dimensions, scale, warnings, and content hash.

Acceptance: Repeating export with unchanged inputs produces geometrically identical output and the same canonical content hash.

MD-10P1

Named presets and comparisons

Users may save token presets, compare two designs side by side, and promote one preset to approved.

MD-11P1

Controlled local overrides

If enabled, event-specific overrides must be explicit, visually badged, listed in preflight, and individually resettable. Overrides are disabled by default.

MD-12P2

Illustrator-native rebuild

An optional JSX exporter may rebuild the timeline in Illustrator using real Area Type and named layers. It consumes the same records and tokens but is not required for the browser MVP.

08

Canonical data model

Three explicit inputs replace information hidden in the artwork.

Timeline records

timeline-milestones.json

Order, date, headline, caption, photo, era, reference, rights, provenance, and review state.

Design tokens

timeline-design-tokens.json

Dimensions, typography, spacing, color, shadow, scale, ramp geometry, and export settings.

Preview fixtures

timeline-preview-fixtures.json

Master sample copy, maximum-length cases, empty states, and regression-test content.

Illustrative token contract

{
  "schemaVersion": 1,
  "units": "full-size-inches",
  "document": { "width": 356, "height": 120, "outputScale": 0.1 },
  "ramp": { "angleDegrees": 5, "startX": 28, "startY": 32 },
  "module": {
    "width": 13.6,
    "headlineHeight": 5.4,
    "lowerHeight": 17.32,
    "contentInset": 0.85,
    "photoHeight": 9.9,
    "cornerRadius": 0.4
  },
  "type": {
    "family": "Georgia",
    "dateSize": 1.55,
    "headlineSize": 0.78,
    "headlineLeading": 0.88,
    "captionSize": 0.62
  }
}

Data rules

  • IDs are stable and never derived from display order.
  • Line wrapping is not stored in content; only intentional editorial breaks may be stored.
  • Dates preserve uncertainty and display language rather than forcing false precision.
  • Photo rights, source, and credit remain attached to the image record.
  • Every migration produces a field-level report showing copied, defaulted, and unresolved values.

09

Layout and propagation model

For ordered event index i, the layout engine computes the center point from the selected pitch or fit-to-width mode:

x(i) = startX + i × pitch
y(i) = startY + (x(i) − startX) × tan(rampAngle)

moduleTransform(i) = translate(x(i), y(i))
moduleRotation(i) = 0°

All internal module geometry uses local coordinates relative to the event dot. The timeline line is angled; modules and their text areas remain level.

Required propagation graph

Canvas or inspector edit→Design token→Shared module→All timeline instances→Preflight and export

Override policy

MVP stores no per-event geometry. A future override system may permit narrowly defined exceptions, but every override must name the token it replaces, remain visible in the UI, and appear in the export manifest.

Color-management boundary

The browser renderer is expected to produce RGB output. The print workflow must document the target ICC profile and perform CMYK conversion and final preflight in an appropriate production tool unless browser-PDF testing proves the printer accepts the RGB PDF unchanged.

11

Quality and nonfunctional requirements

Performance

  • Token changes update twenty modules within one animation frame under normal desktop conditions.
  • Dragging remains visually responsive at 30 fps or better.
  • Preflight results update within 250 ms after an edit settles.

Accessibility

  • Every canvas operation has a keyboard and inspector equivalent.
  • Focus order, labels, status announcements, and color contrast meet WCAG 2.2 AA.
  • Warnings never rely on color alone.

Reliability

  • Inputs validate against versioned schemas.
  • Autosave cannot overwrite the approved revision.
  • Export uses an immutable snapshot of records and tokens.

Compatibility

  • Desktop-first support for current Chromium browsers.
  • Read-only review remains usable on tablets.
  • Fonts are checked against the export environment.

Verification strategy

  • Unit tests for token validation, ramp math, era coverage, ordering, and overflow classification.
  • Component tests proving design changes propagate to all instances.
  • Regression fixtures for the master sample and longest production copy.
  • Visual snapshots for all four eras and representative module states.
  • Export tests for page dimensions, font embedding, image inventory, and deterministic hashes.
  • Manual print-preflight checklist before production approval.

12

Delivery phases

  1. Phase 1

    Canonical model and shared component

    Create token and fixture schemas, migrate current content, implement the HTML module, and reproduce the approved visible style.

  2. Phase 2

    Module designer and inspector

    Add selection, direct manipulation, numeric editing, zoom, rulers, snapping, design/content modes, and undo/redo.

  3. Phase 3

    Automatic timeline and content editing

    Render the full five-degree layout, support add/remove/reorder, calculate eras, and connect catalog records and photos.

  4. Phase 4

    Preflight and production export

    Add overflow and asset checks, immutable export snapshots, PDF/SVG/manifest output, regression tests, and live verification.

  5. Phase 5

    Optional production extensions

    Evaluate controlled overrides, named comparisons, Illustrator JSX rebuild, and print-vendor-specific color automation.

14

Open decisions

Recommended: PDF

What must the printer receive?

Confirm whether a print-ready PDF is sufficient or whether an editable Illustrator file is contractually required.

Recommended: disabled

Should local geometry overrides exist?

Keep them out of MVP unless a real production case cannot be solved through shared tokens or content fitting.

Recommended: bundled fonts

How will fonts be licensed and loaded?

Identify exact production font files and confirm embedding permissions before export work begins.

Recommended: external preflight

Where will CMYK conversion occur?

Choose Acrobat, Illustrator, or the print vendor’s workflow and record the target ICC profile.

Recommended: browser-local MVP

Where should drafts live?

Begin with local storage plus explicit JSON export/import; add cloud persistence only if collaboration becomes necessary.

Recommended: same component

How should era labels be edited?

Use a specialized state of the shared module visual system rather than a separately styled label implementation.

Proposed next milestone

Build a vertical slice containing the shared HTML module, design-token file, preserved master fixture, module canvas, inspector controls for typography and three structural dimensions, and a read-only twenty-event timeline preview. Use that slice to validate text flow, propagation, and print geometry before implementing the complete editor.
